The bound was verified by decoding the minted token's claims — `exp` present and exactly 90.00 days out — rather than trusting the create command, because a missing `exp` would have left the token permanent **without any error being raised**. Sequence rotate → mint → verify → wire → redeploy took a 60s window (rotate 1s, mint 5s, verify 6s, wiring 10s, redeploy `Ready` 47s), and the previous token `a09d0413229e` went 200 → **401** at t+2s. The CLI default `-e never` is what made every earlier straggler permanent; **no never-expiring database token now remains live**. *What this buys and what it does not:* it caps how long any straggler credential can stay valid and forces a rotation to actually occur on a schedule — it does not heal or re-verify anything. The cost is symmetrical: if nothing rotates by `2026-12-21T13:07Z`, Production and Preview DB-backed routes fail, and this app has no alerting that would announce it first, so the date is queued as a hard deadline in §7. Scope note: the other `.env` secrets (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`) are static keys with no expiry equivalent, so this control covers the database token only.

The group form, `turso group tokens invalidate default -y`, prints `Success! Tokens invalidated successfully.` but retires nothing: two probe tokens minted *immediately before* the call still authenticated afterwards (`200`), and the pre-existing token `c35bf3cb461c` survived at +0s, +20s, +40s and again at +45s. Turso's docs claim the opposite ("all existing tokens will no longer be valid and will need to be regenerated"), so this is a docs-versus-behaviour gap, not a misuse of the command. **Consequence — resolved 2026-09-23:** the seven tokens named above (`d63c8255868a` from the 2026-09-18 migration, plus `c35bf3cb461c`, `0b2f005cb47c`, `8784ed46c478`, `f6f5d5ed4992`, `f64e3de575cc`, `cf702c61ef72`) are **all dead** — rotating the *database* signing key invalidated every one at once, proven by a pre-rotation snapshot falling 200 → **401** one second after the call. **The earlier conclusion here — that database tokens are non-revocable — was wrong**: it was a wrong-lever problem, not a platform limitation. **The real revoke path:** `POST https://api.turso.tech/v1/organizations/{org}/databases/{db}/auth/rotate` (returns `200`, no body; Turso's docs note "a short downtime is required"). SQL-engine tokens are stateless JWTs with no server-side record, so **no per-token revoke exists** and key rotation is the only mechanism — by design, not by bug. Driving the API requires a real platform credential: the CLI's own `~/.config/turso/settings.json` `token` is **not** one (rejected as `token contains an invalid number of segments`), so mint a scoped one — `turso auth api-tokens mint <name> --org <org> --group <group> --scope read --scope db:rotate-creds` — then revoke it, since API tokens, unlike SQL tokens, *are* revocable. `turso db tokens invalidate` silently redirects to the group form and therefore does **not** do what its name implies; do not reach for it to retire database tokens.
